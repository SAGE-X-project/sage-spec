### 0.2 Classes

- **(a) text fix**: the text is wrong, vague or silent, and the correct behaviour is already fixed by the other text, the vectors, or (where draft.1 §6 made it normative because the text was silent) the Go core. No correct peer changes a byte.
- **(b) normative tightening**: a new MUST/MUST NOT, limit, strictness or replay rule that every *correct* draft.1 signer or sender still satisfies. Only receivers change.
- **(c) wire-changing**: changes bytes that correct peers sign, send, derive or accept.

"Correct draft.1 peer" means: follows every explicit draft.1 rule and reproduces the vectors; where the text was silent or ambiguous, behaves as the Go core (draft.1 `00:81-83`). A rule is (b) only if every behaviour so defined stays accepted. Where I had to make a judgment call, the item says so and says what class it would be under the other reading.

Items marked **b-limit** introduce a numeric bound where draft.1 had none. Every bound is set far above what the reference implementations produce; strictly read, a peer that exceeded it was draft.1-conforming. If the owner treats any newly bounded field as wire-changing, move the b-limit items to (c); no other item changes class.

### 0.3 Item layout

Each item: ID, class, title; **Now** quotes the draft.1 text; **Fix** is the replacement text (normative wording to paste); **Why**; **Code** lists the sage lines that must change or that show the behaviour; (c) items add **draft.2**, **0.10.0** and **Risk if left**.

"Code gap" items (text already right, code wrong) are collected at the end of each chapter and are not counted as defects.

## 1. Chapter 00 Overview

#### E00-01 (a) The text and the vectors are normative; no implementation is

**Now** `00:79-84`: "Until the Rust core is aligned, the Go core is normative where this text is silent or ambiguous; each section cites the Go source files it was derived from. Discrepancies between this text and the Go core are bugs in this text and are fixed here first, with a vector." Also `VR:3-4`: "Generated by `sage-vectors gen` from the Go core ... do not edit by hand."

**Fix** (replaces §6 in full):

> ## 6. Normative status
>
> This text and the vectors in `vectors/` are the specification. Where the text and a vector disagree, the disagreement is a defect of this specification; until it is corrected, an implementation MUST reproduce the vector. No implementation is normative. Where this text cites a source file ("Go sources: ..."), the citation is informative: it records where a rule came from, not what the rule is.
>

>

In `VR:3-4`: "Each file is produced by a reference generator and checked by every conforming implementation. The files are normative (`spec/00-overview.md` §6); a regeneration that changes any input or output byte is a specification change."

**Why**. Requested. Draft.1's rule made every text/code discrepancy a text bug, so an independent implementation could not know what to implement. This errata writes out every behaviour that rule imported (all class-(a) items marked "documents Go"), so the new rule does not orphan anything.

**Code**. None on the wire. `sage/pkg/vectors/vectors.go:57-58` comment and constant (see E00-08).

#### E00-05 (a) Conformance levels name chapters, include 07/08, and include negative vectors

> | Level | Chapters | Vector suites | Typical implementer |

> | Verifier | 01, 02, 03, 06, 07 | `crypto`, `jcs`, `rfc9421`, `did` (including the card vector) | a gateway or inspector |

#### E00-06 (a) Versioning before 1.0 and how the version is reported

**Now** `00:69-77`: "A change that alters bytes on the wire ... is breaking and increments MAJOR. ... Implementations report the specification version they conform to alongside their own version."

**Fix**:

> - Before `1.0.0`, a breaking change increments MINOR (0.9.x to 0.10.0) and a compatible change increments PATCH. From `1.0.0`, breaking changes increment MAJOR.
> - Breaking means: it alters bytes on the wire, a derivation label, a covered component set, a key or signature encoding, or makes a rejection rule accept something it rejected before.
> - 0.9.0 carries no version on the wire (E00-07). Implementations report the version they conform to out of band (documentation, `--version` output, conformance reports). A 0.9.0 peer and a 0.10.0 peer fail each other's checks because their labels differ (`sage/hpke-info|v1` versus the 0.10.0 labels); they do not misinterpret each other.

**Why**. The owner's plan (0.9.0, then draft.2, then 0.10.0 as a breaking release) contradicts "increments MAJOR". "Report alongside their own version" had no mechanism. **Code**: `sage/cmd/sage-vectors/main.go:51` only.

#### E00-07 (c) No protocol version on the wire

**Risk if left**: low. Cross-version traffic fails closed because the HPKE and session labels differ. The cost is diagnostics: a peer cannot tell "wrong version" from "forged". **Decision**: deferred.

## 2. Chapter 01 Cryptographic primitives

#### E01-01 (a) Which key types a did:sage record can carry

**Now** `01:9-18`: table lists Ed25519, secp256k1, P-256, X25519, RSA; "On-chain and in agent cards the registry key type is an integer: ECDSA (secp256k1) = 0, Ed25519 = 1, X25519 = 2."

**Fix**: append: "A 0.9.0 registry record can only carry types 0, 1 and 2. P-256 is defined for signatures (vectors `crypto/p256-sha256-sign`, `rfc9421/request-ecdsa-p256-sha256`) but no 0.9.0 did:sage record can publish a P-256 key, so a P-256 signature is verifiable only with a key obtained by a means outside this specification. The integer is a registry storage code, not an algorithm identifier."

**Why**. `06:45` has the same three types; the text implies P-256 agents exist. **Code**: `sage/pkg/agent/did/types_v4.go:40-44`.

#### E01-02 (b) RSA is not part of 0.9.0

**Now** `01:15` (RSA row), `01:59-64` (§RSA), `01:73` (`rsa-pss-sha256`), O-3 at `01:94`.

**Fix**: delete the RSA row and §RSA; replace with: "RSA is not part of this specification. Signers MUST NOT use RSA keys. Verifiers MUST reject a signature whose `alg` is `rsa-pss-sha256` or any RSA algorithm, and MUST reject an RSA public key." Close O-3.

**Why**. (b) because no correct draft.1 peer can use RSA through this specification: the registry has no RSA type (E01-01), `keyid` must be a did:sage DID (`03:45`), and there is no vector. The identifier also named the wrong operation (PKCS#1 v1.5 labelled PSS). If any deployment verifies RSA keys from a key file outside did:sage, treat this item as (c) for that deployment. **Code**: `sage/pkg/agent/crypto/keys/rs256.go:75-79`, `sage/pkg/agent/crypto/algorithm_registry.go:103`, `sage/pkg/agent/core/rfc9421/verifier_http.go:495-499`.

#### E01-03 (a) secp256k1 public key encodings

**Now** `01:12`: "65-byte uncompressed SEC1 (`04 || X || Y`); 33-byte compressed accepted where noted". Nothing is noted anywhere.

**Fix**: "The canonical encoding is 65-byte uncompressed SEC1. A registry record's `key_data` for type 0 MAY be 33-byte compressed, 64-byte `X || Y` or 65-byte uncompressed; a verifier MUST decode all three to the same point and MUST reject any other length. KeyID (§4), the Ethereum address and the agent card (07) use the 65-byte form. The proof of possession (06 §4) uses `key_data` exactly as stored." (documents Go)

**Why**. The contract does not check ECDSA `keyData` length (`contracts/ethereum/contracts/AgentCardRegistry.sol:409-428`); Go accepts 33, 64 and 65 bytes. **Code**: `sage/pkg/agent/did/utils.go:74-85`.

#### E01-04 (b) Ed25519 verification is strict

**Now** `01:24-25`: "Pure Ed25519 over the message bytes. No pre-hash, no context string. Signature: 64 bytes `R || S`."

**Fix**: add: "Verifiers MUST implement RFC 8032 §5.1.7 with the cofactorless equation `[S]B = R + [k]A`, and MUST reject: a signature that is not 64 bytes; `S >= L`; a non-canonical encoding of `A` or `R` (y >= p); a public key `A` of small order (the eight torsion points). Registries and verifiers MUST reject a small-order public key."

**Why**. An honest signer never produces these, so (b). Without it two libraries can disagree on the same signature, and a small-order public key verifies forged signatures for many messages (an attacker can register such a key, since the contract does not check Ed25519 keys at all, E06-09). **Code**: `sage/pkg/agent/crypto/keys/ed25519.go:69-77`, `keys/verify.go:45-49`. Go's `crypto/ed25519` rejects `S >= L` but, per its documentation as I recall it, accepts non-canonical and small-order `A` (not run; see §12).

#### E01-05 (b) secp256k1 verification accepts exactly one encoding

**Now** `01:38-41`: "Verifiers MUST accept 65-byte `r || s || v` and 64-byte `r || s`, and SHOULD accept ASN.1 DER. Verifiers MUST normalise a high-S value before checking so that signatures produced by other libraries remain verifiable."

**Fix**: "Verifiers MUST accept only a 65-byte `r || s || v` with `1 <= r, s < n`, `s <= n/2` (low-S) and `v` in {0, 1}, and MUST check that the public key recovered with `v` equals the resolved key. A 64-byte signature, a DER signature, a high-S signature and `v` in {27, 28} MUST be rejected." Delete the "and vice versa" claim at `01:43-44` or restrict it to "a wallet that signs the raw Keccak digest and returns `v` in {0, 1}".

**Why**. (b): every correct signer must already emit 65 bytes, low-S, `v` in {0,1} (`01:32-36`, and 06 §4 PoP). Accepting 64 B, DER and both `s` values makes every signature malleable into at least four byte strings; any cache, dedupe or log keyed on signature bytes can be bypassed. **Code**: `sage/pkg/agent/crypto/keys/secp256k1_keccak.go:48-59` (truncates `v` unchecked, normalises high-S), `keys/verify.go:55-57` (DER), `sage/pkg/vectors/crypto.go:118` (the vector checker verifies the 64-byte form; it must stop; vector bytes unchanged, see §11).

#### E01-06 (b) P-256 verification accepts exactly one encoding

**Now** `01:56-57`: "The RFC 9421 verifier accepts raw only; the generic verifier also accepts DER."

**Fix**: "Verifiers MUST accept only the 64-byte raw `r || s` with `s <= n/2`; DER and high-S MUST be rejected on every path." Signers already low-S (`01:55`).

**Why**. Same malleability as E01-05; one path-dependent rule is a differential. **Code**: `sage/pkg/agent/crypto/keys/verify.go:63-65`, `keys/p256.go:153-163`.

#### E01-07 (a) O-1 closed: the PoP digest is a distinct, documented algorithm

**Now** `01:46-48`: "*Exception.* The key proof of possession in `06-did-sage.md` signs SHA-256 of its challenge string ... listed as open item O-1."

**Fix**: "The proof of possession of `06-did-sage.md` §4 is a separate algorithm: for both Ed25519 and secp256k1 the signed message is `SHA-256(challenge)` (32 bytes), and for secp256k1 the 32-byte digest is signed directly (no Keccak). It is valid only as a proof of possession and MUST NOT be accepted on any other path." Remove O-1 from §5.

**Why**. `vec:did/pop-ed25519` and `vec:did/pop-secp256k1` pin it; changing it is a wire change that 0.10.0 makes. **Code**: `sage/pkg/agent/did/key_proof.go:46-82`.

#### E01-08 (a) O-2 closed: P-256 signing stays randomised

**Now** `01:53-54`: "RFC 6979 is RECOMMENDED and will become REQUIRED (open item O-2)."

**Fix**: "RFC 6979 is RECOMMENDED. Randomised signing is permitted; verification is deterministic, so P-256 vectors are verify-only." Remove O-2.

**Why**. Making RFC 6979 REQUIRED would make the Go signer non-conforming without any security gain. **Code**: `sage/pkg/agent/crypto/keys/p256.go:108-119`.

#### E01-09 (a) What `es256k` means

**Now** `01:71`: "secp256k1 | `es256k`".

**Fix**: add: "`es256k` in this specification is SAGE's name for secp256k1 over Keccak-256 with 65-byte `r || s || v`. It is not JOSE `ES256K` (SHA-256, 64 bytes) and is not registered in the IANA HTTP Signature Algorithms registry; generic RFC 9421 or JOSE libraries will not verify it."

**Why**. Prevents a third party from implementing JOSE semantics. **Code**: `sage/pkg/agent/crypto/algorithm_registry.go:78`.

#### E01-10 (c) Rename `es256k`

**Fix (minimal)**: replace `es256k` with a SAGE-specific name (0.10.0 uses `sage-secp256k1-keccak256`) and forbid `es256k`.

**draft.2**: no; `d2:11:30` lists `es256k` as "current". **0.10.0**: yes.

**Risk if left**: low. A digest mismatch makes cross-interpretation fail verification; no forgery follows. Breaks `vec:rfc9421/request-es256k` (the `alg` string is in the signature base). **Decision**: deferred; E01-09 applies in 0.9.0.

#### E01-11 (b) Algorithm comes from the key, never from the DID's chain

**Now** `01:75-77`: "The `alg` parameter is informative: verifiers select the algorithm from the resolved key type and MUST reject a signature whose `alg` contradicts the key."

**Fix**: add: "`alg` MAY be absent. A verifier MUST select exactly one algorithm from the resolved key's type (Ed25519 → `ed25519`, secp256k1 → `es256k`, P-256 → `ecdsa-p256-sha256`), MUST NOT try another, and MUST NOT infer the algorithm from the DID's chain or any other part of the identifier."

**Why**. (b): correct signers sign with their own key's algorithm. The legacy Message verifier picks secp256k1 for every `ethereum` DID even when the resolved key is Ed25519. `alg` stays optional because the reference ResponseSigner omits it when not configured (`sage/pkg/agent/core/rfc9421/response_signer.go:65-69`). **Code**: `sage/pkg/agent/crypto/algorithm_registry.go:298-324`, `sage/pkg/agent/core/verification_service.go:159-173`.

#### E01-12 (a) KeyID input for secp256k1

**Now** `01:81-82`: "`KeyID(pub) = hex(SHA-256(pub)[0:8])` over the raw public key bytes of section 1".

**Fix**: "... over the canonical encoding of §1 (65-byte uncompressed for secp256k1 and P-256, 32 bytes for Ed25519 and X25519)."

**Why**. `vec:crypto/secp256k1-keccak-sign` computes `key_id` over 65 bytes; the Go secp256k1 key pair uses the compressed form. **Code**: `sage/pkg/agent/crypto/keys/secp256k1.go:46-47`, `keys/constructors.go:56-58` (must use 65 bytes).

#### E01-13 (b) KeyID is for logs only

**Now** `01:82-83`: "It is used for key selection and logging, not as a security binding."

**Fix**: "It is used for logging and diagnostics only. It MUST NOT be used to select a key, to look up a session, or to make an authorisation decision."

**Why**. A 64-bit truncated hash collides in 2^32 work; selection by it lets a crafted key shadow another in local stores. KeyID is not on the wire (`keyid` in 03 is a DID; `kid` in 04 is `kid-<uuid>`), so no peer is affected. **Code**: none on the wire; audit local stores (`sage/pkg/agent/crypto/storage`).

#### E01-14 (b) Public key validation

**Now**: nothing.

**Fix**: "A verifier MUST reject a secp256k1 or P-256 public key that is not a valid point on the curve or is the point at infinity, an Ed25519 key per E01-04, and an X25519 key that is not 32 bytes. X25519 public keys from a peer (`enc`, `ephC`, `ephS`) are checked by the all-zero shared-secret rule of `04-hpke.md` §3."

**Why**. Invalid-curve inputs are the classic ECDH/ECDSA failure. **Code**: `sage/pkg/agent/did/utils.go:74-90` (uses `secp256k1.ParsePubKey`, which validates).

**Code gaps, chapter 01**: none beyond those cited above.

## 3. Chapter 02 JSON canonicalisation

#### E02-01 (a) Which members are removed before verifying (resolved SN-3)

**Now** `02:33-35`: "Verifiers ... MUST remove exactly the members listed above before canonicalising." The table at `02:26` lists the twelve members that are *signed*, not removed.

**Fix**: replace the table and the paragraph with:

> | Object | Signed by | Member removed before JCS | Section |
> |---|---|---|---|
> | HPKE response envelope | responder | `sigB64` | `04-hpke.md` §6 |
> | A2A agent card | card owner | `proof` | `07-a2a.md` §3 |
> | `WireMessage` | sender | `signature` | `08-transport.md` §1 |
> | `WireResponse` | responder | `signature` | `08-transport.md` §2 |
>
> Verifiers MUST canonicalise the received JSON object themselves, after removing exactly the one top-level member named for that object. No nested member is removed. The values the verifier acts on MUST come from the same parsed object it canonicalised.

**Why**. Read literally, the rule removes the signed members. The two transport rows follow from E08-01 and E08-02. **Code**: `sage/pkg/agent/did/a2a_proof.go:77-89`, `sage/pkg/agent/hpke/client.go:393-403` (both already do the intended thing); the transport has no JSON signature today (`sage/pkg/agent/transport/wire.go:25-43`).

#### E02-02 (b) Duplicate member names are rejected

**Now**: silent; Go keeps the last duplicate.

**Fix**: "A JSON text that is verified against a signature (HPKE init and response, agent card, `WireMessage`, `WireResponse`) MUST be rejected if any object in it, at any depth, has two members with the same name (compared as sequences of Unicode code points after unescaping)."

**Why**. A signer never emits duplicates (it serialises from a struct), so (b). With last-wins, the canonical bytes and the value the application reads can still agree in Go but disagree in another parser: a signature differential. **Code**: `sage/pkg/agent/internal/rfc8785/rfc8785.go:20-27` (documents that it does not reject), `sage/pkg/agent/crypto/jcs/jcs.go:30-32`, `sage/pkg/agent/hpke/common.go:258` (`json.Unmarshal` into a map).

#### E02-03 (b) One parse, exact names

**Now**: silent.

#### E02-05 (b) Numbers in signed SAGE objects (updated for SN-2)

**Why**. Every member of the HPKE envelopes and the card is a string, array or object of strings (`04:85-116`, `07:12-31`; the card's `capabilities` is an array of strings, `sage/pkg/agent/did/a2a.go:138-147`); the transport envelopes have strings, one object of strings (`metadata`) and one boolean (`success`). #### E02-06 (b, b-limit) Size and depth of signed JSON

**Now**: silent.

**Fix**: "A verifier MUST reject a signed JSON text nested deeper than 16 levels, with an object of more than 256 members or an array of more than 256 elements, or larger than 64 KiB for the HPKE envelopes and the agent card. `WireMessage` and `WireResponse` are bounded by the 1 MiB transport limit (`08-transport.md`, E08-10) instead, because their `payload` or `data` carries application bytes. **Now** `03:22-23`: "the parameters exactly as in `Signature-Input`."

#### E03-06 (b) Exactly one signature label

**Now** `03:69-70`: "the label to verify is given by the caller or is the lexicographically first label."

**Fix**: "A signer MUST emit exactly one label in `Signature-Input` and the same single label in `Signature` (default `sig1`). **Why**. Every Go signer emits one label. "Lexicographically first" lets anyone on the path add a label `a...` signed by their own key; combined with the gateway's map-order key selection (`gateway/pkg/gateway/verify/verify.go:90-94`) the verified signature and the identity it reports can come from different labels. **Code**: `sage/pkg/agent/core/rfc9421/verifier_http.go:310-339`, `parser.go:66-71` (a repeated label: last wins).

**Now** `03:24-25`: "multiple header values are joined with `", "` and trimmed."

**Fix**: add: "A request or response with more than one field line of `Signature-Input`, `Signature`, `Content-Digest` or `X-SAGE-DID` MUST be rejected. For other covered fields, field lines are combined as RFC 9421 §2.1 specifies."

**Why**. Go reads only the first `Signature-Input` and `Signature` line (`verifier_http.go:311,320`), so a second line is invisible to it but visible to a proxy. **Code**: `verifier_http.go:311,320`; `body_integrity.go:71-99`.

#### E03-08 (c) Derived components restricted to the unambiguous set

**Now** `03:27-30`: "Derived components implemented: `@method`, `@target-uri`, `@authority`, `@scheme`, `@request-target`, `@path`, `@query` (an empty query yields `?`), `@query-param`, and `@status`."

**Fix (minimal)**: "Signers MUST cover only `@method`, `@target-uri`, `@authority`, `@scheme`, `@query`, `@status` (responses) and their `;req` forms (responses). **Why**. All vectors cover only `@method @target-uri @authority`, so this is vector-compatible. **Decision**: applied.

#### E03-09 (b) Component parameters

**Now**: silent.

**Fix**: "A covered component MUST NOT carry any parameter other than `;req` (responses only). A verifier MUST reject `;sf`, `;bs`, `;key`, `;tr`, `;name` and any unknown parameter."

**Why**. Go ignores them (`canonicalizer.go:128-180`) and canonicalises the plain component, so a signer that meant `;sf` and the Go verifier sign different bytes. No correct draft.1 signer emits them: Go, which was normative where the text was silent, does not implement them. **Code**: `canonicalizer.go:128-180`.

#### E03-10 (c) Strict verification is the only mode (closes O-5)

**Now** `03:34-43`: "Signers SHOULD cover, in this order: ... Verifiers in strict mode REQUIRE `@method`, `@target-uri`, `@authority`, `content-digest` when a body is present, and a `nonce`." `03:65`: "Verifiers REQUIRE `@status` and, in strict mode, request binding."

>

**Why**. Draft.1 let a signer omit the nonce and body digest, and let a responder omit request binding, whenever the verifier was not "strict"; a signer cannot know which it faces. Without a nonce a captured request can be replayed for `MaxAge` (forever with `MaxAge = 0`, see E03-11); without `content-digest` the body can be replaced; without `signature;req` a response can be bound to a different request with the same method and URI. All four rfc9421 vectors already satisfy the fix. **Decision**: applied.

#### E03-11 (b) Freshness cannot be disabled

**Now** `03:73-76`: "reject when `now - created > MaxAge` (default 5 minutes; zero disables the check, which the vectors rely on), when `created` is more than `MaxClockSkew` (default 5 minutes) in the future, or when `expires` has passed."

**Fix**: "A verifier MUST reject when `now - created > MaxAge`, when `created - now > MaxClockSkew`, when `expires` is present and `expires <= created`, or when `expires` is present and `now >= expires`. `MaxAge` MUST be greater than 0 and at most 300 seconds (default 300). `MaxClockSkew` MUST be at most 300 seconds (RECOMMENDED 60). **Why**. Correct signers use the current time, so they pass. "Zero disables" exists only for the vectors, which can fix the verification time instead. In Go, skew 0 silently becomes the 5-minute default (`verifier_http.go:363-366`). **Code**: `verifier_http.go:353-374,589-594`; `sage/pkg/vectors/rfc9421.go:155,258` (use a fixed clock instead of `MaxAge: 0`); vector descriptions "Verify with MaxAge disabled" change (description text only).

#### E03-12 (b, partly b-limit) Replay scope, retention and nonce form

**Now** `03:80-82`: "check the `nonce` against the replay guard scoped by `keyid` ... The window is the verifier's `MaxAge`."

**Fix** (updated for SN-6): "After the signature verifies and every other check of §5 has passed, as the last step, the verifier MUST check and reserve `(signer DID, nonce)` in its replay store, where the signer DID is the canonical DID of `keyid` (`06-did-sage.md` §2), and MUST reject a pair it has seen. **Why**. #### E03-18 (a) Complete verification order (resolved SN-6)

**Now** `03:69-85` (no resolution step; X-SAGE-DID only in §3; replay at step 5 before `Content-Digest` at step 6).

**Fix**: replace the list with:

> 1. Parse `Signature-Input` and `Signature` (E03-05, E03-06, E03-07); select the label.
> 2. Check parameters and covered components (E03-01, E03-03, E03-08, E03-09, E03-10).
> 3. Check `keyid` (E03-14), derive its DID, and if `X-SAGE-DID` is present require it to equal that DID after canonicalisation (`06` §2); check `ExpectedDID`, `ExpectedKeyID` and (requests only) `ExpectedAuthorities` when set.
> 4. Resolve the DID (`06` §3); reject an unknown or inactive agent; select the key (`06` §3.1).
> 5. Timing (E03-11).
> 6. Rebuild the base from the received message (and the request, for a response) and verify the signature with the key's algorithm (`01`).
> 7. `Content-Digest` against the buffered body (E03-13).
> 8. Replay: check and reserve `(signer DID, nonce)` (E03-12). This is the last step; a message that fails any earlier step does not consume its nonce.

**Why**. The resolution and inactive checks were only in 06. **Now** `05:8-16`: "Inputs: a shared secret (the HPKE seed of `04-hpke.md` §3, or another 32-byte secret), the context id, both ephemeral public keys and a label. ... salt = SHA-256(label || ctxID || lo || hi); seed = HKDF-Extract(SHA-256, sharedSecret, salt); sid = base64url-raw(SHA-256(label || seed)[0:16])".

#### E05-04 (c) Shared keys allow reflection; peers use directional keys only

**Now** `05:29,34-36`: "64 bytes: `encryptKey[32] || signingKey[32]` (shared, non-directional) ... The shared keys exist for `Encrypt`/`Decrypt` callers that do not use roles; role-aware sessions use the directional keys and MUST NOT mix the two on one record stream."

**Fix (minimal)**: "A session established by `04-hpke.md` MUST use only the directional keys, for every record in both directions, and a receiver on such a session MUST NOT attempt to open a record with the shared keys. **Why**. **Risk if left**: high: authenticity of direction is lost (a peer's own message is accepted as the other side's). Vector-compatible: `encrypt-decrypt` stays valid as a key-schedule and rotation vector. **Decision**: applied.

#### E06-08 (a) What the record really says, and what a verifier reads from it (resolved SN-8)

**Now** `06:41-50`: record table; `keys[] {type, key_data, signature, verified, created_at}`.

**Fix**: add after the table:

> - `keys[]` lists the agent's current keys in registry order. Revoking a key removes it from this list (the registry keeps the key's own entry for audit, outside the list).
> - `signature` of a type-0 or type-1 entry is the proof of possession of §4. A type-2 entry has no proof (§4).
> - `verified` is a flag kept by the registry. A verifier MUST NOT use it to decide whether a key may be used: key eligibility is defined in §3.1 from the listing and the §4 proof alone.
> - Implementations may expose a selected-key view (`public_key`); it is derived by §3.1 and is not a registry member.

**Why**. `06:65-66` already says verifiers recompute the proof, which makes the flag redundant for a verifier; D2 = C makes that the only rule. #### E06-09 (c) Key possession is not proven or verifiable

**Now** `06:54-66`: "Each registered signing key carries a signature proving control of the private key ... Verifiers recompute the challenge from the DID and `key_data` and verify `signature`; a key whose proof fails MUST NOT be marked `verified`."

**Fix (applied, D2 = C; updated for SN-8)**: "`keys[].signature` of a type-0 or type-1 key MUST be the §4 proof, with the challenge unchanged and the DID taken from the record's `did` member exactly as stored. A verifier MUST verify the proof itself before using the key, independently of the registry, and MUST NOT rely on the registry's `verified` flag (§3, §3.1)." ## 9. Chapter 08 Transport envelope

#### E08-01 (c) The envelope is not signed

**Now** `08:22-24`: "`signature` is the sender's signature over `payload` with the algorithm of `01-crypto.md` selected by the sender's registered key."

**Fix (applied; resolved SN-2)**: replace §1 with:

> ```json
> {
>   "id": "<message id>",
>   "context_id": "<optional>",
>   "task_id": "<optional>",
>   "payload": "<base64 bytes>",
>   "did": "<sender DID>",
>   "recipient": "<receiver DID>",
>   "created": "<YYYY-MM-DDThh:mm:ssZ>",
>   "nonce": "<16-64 characters>",
>   "metadata": { "<key>": "<value>" },
>   "role": "<optional>",
>   "signature": "<base64 bytes>"
> }
> ```
>
> - `created` is a JSON string: an RFC 3339 `date-time` in UTC, written exactly as `YYYY-MM-DDThh:mm:ssZ` (upper-case `T` and `Z`, no fractional seconds, no numeric offset). Any other form MUST be rejected. It is a string, not a number, because signed SAGE objects contain no numbers (`02-jcs.md`, E02-05).
> - `nonce` has the syntax of `03-rfc9421.md` §5 (E03-12); `recipient` is the DID the sender addresses.
> - Optional members that are absent are omitted, not sent as `null` or `""`. Every member is a string except `metadata`, an object whose values are strings.
> - Signing input: `REQUEST_LABEL || JCS(envelope without signature)`, with `REQUEST_LABEL` from §6. `signature` is standard base64 of the signature by the sender's `06` §3.1 signing key (E08-16).
> - A receiver MUST, in this order: check sizes and syntax (E08-10, E08-11, `02` E02-02 to E02-06); require `recipient` to equal its own DID and `did` to name an active agent (canonical comparison, `06` §2); require `now - 300 s <= created <= now + MaxClockSkew` (skew as in E03-11); verify `signature`; and, last, check and reserve `(did, nonce)` in a replay store retained at least until `created + 300 s + MaxClockSkew`, with the store rules of E03-12.

**Why**. `id`, `context_id`, `task_id`, `did`, `metadata` and `role` were outside the signature. An attacker could move a signed payload into another context or task, change `metadata` (including `cookie`) and `role`, replay the message indefinitely, and, with E06-09, swap `did` to a DID that registered the victim's key. One fixed text form of `created` keeps the JCS bytes unique: RFC 3339 allows several spellings of the same instant (`z`, `+00:00`, fractional seconds), which would otherwise give one envelope several valid signing inputs.

**draft.2**: no (08 unchanged). **0.10.0**: yes (domain-separated JCS signature, `recipient`, `version`, `id`/nonce replay).

**Risk if left**: high wherever 08 carries anything other than the HPKE init. No vector exists, so the fix is vector-compatible; the HPKE init uses it too (E04-04). **Decision**: applied. **Code**: `sage/pkg/agent/transport/wire.go:25-43` (new members), `transport/http/server.go`, `transport/websocket/server.go`, `hpke/client.go:265-284`, `hpke/server.go:228-246`.

#### E08-02 (c) Responses are unsigned and unbound

**Now** `08:31`: WireResponse.

**Fix (applied; resolved SN-4)**: replace §2 with:

> ```json
> { "success": true, "message_id": "<id>", "task_id": "<optional>", "data": "<base64>", "error": "<optional>",
>   "did": "<responder DID>", "created": "<YYYY-MM-DDThh:mm:ssZ>", "request_hash": "<base64url>", "signature": "<base64 bytes>" }

**Now**: the same key signs the RFC 9421 base (03), the HPKE response JCS (04), the PoP digest (06), the card JCS (07) and raw transport payloads (08, the HPKE init included), each without a context prefix (`02:29-31`, `08:22-24`, `06:58-61`).

**Fix (applied to 08; resolved SN-5)**: add §6:

> ## 6. Signing labels
>
> | Constant | Exact bytes (ASCII) | Hex | Length |
> |---|---|---|---|
> | `REQUEST_LABEL` | `sage-wire-request|0.9` followed by one LF (0x0A) | `736167652d776972652d726571756573747c302e390a` | 22 |

The other signing contexts keep their draft.1 bytes (card JCS, HPKE response JCS, PoP digest, RFC 9421 base), because changing them breaks their vectors (deferred). ## 10. Data protection requirements (text for `00-overview.md` §7)

> ## 7. Data protection requirements
>
> These requirements collect, for every chapter, the rules that keep keys, payloads and identities from leaking or being misused. They are normative. Each cites the chapter rule it summarises; where the two differ, the chapter governs.

### DP-1 Input size limits

> A receiver MUST check sizes before parsing, decoding or any cryptographic operation, and MUST reject (not truncate) an oversized input.
>
> | Input | Maximum | Rule |
> |---|---|---|
> | HTTP request body, WebSocket message | 1 MiB | 08 E08-10 |
> | Body buffered for `Content-Digest` | 16 MiB (only where 08 does not apply) | 03 E03-13 |
> | `Signature-Input`, `Signature` field value | 8 KiB each; 32 covered components | 03 E03-21 |
> | HTTP header section | 64 KiB | 03 E03-21 |
> | RFC 9421 `nonce` | 16-64 characters | 03 E03-12 |
> | DID; `keyid` | 256 bytes; 289 bytes | 06 E06-03 |
> | HPKE `ctxID`; init payload; `kid` | 128 characters; 4 KiB; 128 characters | 04 E04-05, E04-06, E04-09 |
> | Any value passed to `len16` | 65 535 bytes | 00 E00-03 |
> | Signed JSON: HPKE envelopes, card | 64 KiB, depth 16, 256 members or elements, 32 card keys and services | 02 E02-06 |
> | Signed JSON: `WireMessage`, `WireResponse` | 1 MiB (transport limit), depth 16, 256 members or elements | 02 E02-06, 08 E08-10 |
> | Session record; caller AAD | 16 MiB + 36 bytes; 4 KiB | 05 E05-08 |
> | Envelope `id`, `context_id`, `task_id`; `role`; `metadata` | 128 B; 32 B; 32 entries, 64 B keys, 1 KiB values | 08 E08-11 |
> | Registry record fields | name 256 B, description 4 KiB, endpoint 2 KiB, 32 keys, capabilities 16 KiB | 06 E06-14 |

### DP-2 Parsing strictness

> 1. Every encoded value has one accepted form. Base64 and base64url values MUST be canonical (correct alphabet, padding as specified, no trailing bits, no whitespace). Hex is lower-case. Signatures: 64 bytes Ed25519 and P-256, 65 bytes secp256k1, low-S, `v` checked (01 E01-04 to E01-06).
> 2. JSON that is signed or verified: no duplicate or case-variant member names, no unpaired surrogates, valid UTF-8, no trailing data, no numbers, exact member sets (02 E02-02 to E02-05; 04 E04-06, E04-09).
> 3. HTTP signatures: one label, one field line per signature-relevant header, canonical `Signature-Input`, no unknown parameters, no component parameters other than `;req`, a fixed set of derived components (03 E03-03, E03-05 to E03-09).
> 4. Identifiers: the did:sage grammar with its character set; comparisons on the canonical form (06 E06-02, E06-04).
> 5. A value the receiver acts on MUST come from the same parse that was verified (02 E02-01, E02-03).

### DP-3 Key handling and lifetime

> 1. Private keys never leave the agent that owns them and MUST NOT appear in any message, log, error or vector other than the label-derived test keys of `vectors/README.md`.
> 2. A key is used for one purpose: X25519 keys only for key agreement; Ed25519 and secp256k1 keys only for signing. Every signature an agent makes is over a context-specific input (08 §6 labels for the envelopes; JCS objects with fixed member sets for the card and HPKE response; the 32-byte PoP digest; the RFC 9421 base), so application bytes carried in `payload` cannot be turned into another context's signature (08 E08-03). An agent MUST NOT sign bytes in any non-envelope context on behalf of another party.
> 3. Ephemeral private keys (`ephC`, `ephS`, the HPKE encapsulation key) are generated per handshake from a CSPRNG, used once, and erased as soon as `seed` is computed. `exporterHPKE`, `ssE2E` and `ackKey` are erased after `ackTag` is computed or checked. `seed` and all session keys are erased when the session ends or expires (05 E05-10).
> 4. A session ends at the earliest of `MaxAge` (at most 24 h), `IdleTimeout`, `MaxMessages`, 2^32 records under one generation key, or the revocation of either peer's key being observed (05 E05-09, E05-10). 0.9.0 has no forward secrecy inside a session: compromise of `seed` exposes every record of that session.
> 5. A key is usable only while it is listed in the agent's `keys[]` and, for a signing key, carries a valid §4 proof that the verifier checked itself; the registry's `verified` flag is not used (06 E06-08, E06-11). A KEM key that is not listed is never used (04 E04-02). Revocation removes a key from the list and reaches verifiers only through resolution, which MUST be at most 300 s old and MUST fail closed (06 E06-12).
> 6. Implementations SHOULD keep long-term private keys in an encrypted store or hardware token, and SHOULD compare secrets, MACs and tags in constant time (`ackTag` MUST, 04 §5).

### DP-4 Replay and freshness

> | Object | Freshness | Replay store | Rule |
> |---|---|---|---|
> | RFC 9421 request | `created` within `MaxAge` (≤ 300 s) and skew (≤ 300 s); `expires` if present | `(signer DID, nonce)` kept ≥ `created + MaxAge + skew` | 03 E03-02, E03-11, E03-12 |
> | RFC 9421 response | as above | bound to the request by `"signature";req` | 03 E03-10 |
> | HPKE init | `ts` within ±120 s | `(ctxID, nonce)` kept ≥ 600 s | 04 §6, E04-14 |
> | HPKE response | bound to the init by `ackTag`, `enc`, `ephC` | none needed | 04 E04-09, E04-17 |
> | Session record | session lifetime | 1024-entry window per direction | 05 E05-11 |
> | Transport request envelope | `created` (`YYYY-MM-DDThh:mm:ssZ`) within 300 s and skew | `(did, nonce)` kept ≥ `created + 300 s + skew` | 08 E08-01 |
> | Transport response envelope | `created` within the same window | bound to the request by `request_hash` | 08 E08-02 |
> | Resolution result | ≤ 300 s for positive results | n/a | 06 E06-12 |
>
> In every store: an entry is checked and reserved only after the signature or AEAD and every other check have succeeded, so a rejected message never consumes a nonce (03 E03-18); a full store rejects new input rather than evicting live entries; a store that was lost rejects input dated before its restoration plus the skew. Freshness checks cannot be disabled outside test harnesses, which fix the clock instead.

### DP-5 Error disclosure

> 1. Every failure of an inbound message before it reaches the application handler (size, syntax, parsing, envelope, freshness, resolution, signature, digest, replay, cookie) produces one externally visible result per transport: HTTP 401 with body `authentication failed` and a constant `WWW-Authenticate` value for RFC 9421; HTTP 200 with the unsigned `{"success":false,"error":"authentication failed"}` for 08, which the HPKE responder also uses. No header, status, body or error string may depend on which check failed (03 E03-17, 04 E04-07, 08 E08-08, E08-09).
> 1a. `internal error` is returned only when the application handler fails after the message was accepted, in a signed 08 response. No `bad request` or other value exists.
> 2. There is no distinct error for a disallowed suite, unknown agent, inactive agent, revoked key, stale timestamp or replay.
> 3. Libraries may return detailed errors to their caller; the component that answers the peer MUST map them.
> 4. Cheap checks (sizes, syntax, cookie) come before resolution and signature verification; this is for cost, not secrecy, and does not permit distinct errors.

### DP-6 Logging

> 1. MUST NOT log: private keys, seeds, `exporterHPKE`, `ssE2E`, `ackKey`, session keys, session plaintext, decrypted payloads, request or response bodies, or cookies.
> 2. SHOULD NOT log full signatures or nonces; log their SHA-256 prefix if correlation is needed.
> 3. MAY log: DIDs, KeyIDs (01 §4), message ids, the diagnostic reason for a rejection, and timestamps.
> 4. Values taken from unverified input (for example the `keyid` DID before the signature verifies) MUST be marked as unverified, truncated to 256 bytes, and escaped so that control characters cannot forge log lines.
> 5. Logs of rejected inputs MUST NOT include more of the input than item 4 allows.
