# 3. HTTP Message Signatures profile

Version: 0.9.0-draft.1.1. Finalizes 0.9.0-draft.1 with the errata in [../docs/errata-0.9.0-draft.1.md](../docs/errata-0.9.0-draft.1.md).

Vectors: `vectors/rfc9421.json`. Go sources: `pkg/agent/core/rfc9421/`
(`canonicalizer.go`, `verifier_http.go`, `parser.go`, `body_integrity.go`,
`response_signer.go`).

Signature formats other than RFC 9421 HTTP message signatures, including the
SAGE core 'Message' format, are not part of this specification and MUST NOT
be accepted in place of one.

## 1. Headers

| Header | Content |
|---|---|
| `Signature-Input` | `<label>=(<components>);keyid="…"[;alg="…"];created=…[;expires=…][;nonce="…"]` |
| `Signature` | `<label>=:<base64 signature>:` (RFC 8941 byte sequence, standard base64) |
| `Content-Digest` | `sha-256=:<base64 SHA-256 of the body>:` |

The default label is `sig1`. A signer MUST emit exactly one label in
`Signature-Input` and the same single label in `Signature` (default `sig1`).
A verifier MUST reject a message whose `Signature-Input` or `Signature`
dictionary has more than one member, whose two dictionaries name different
labels, or that repeats a label, unless the caller has named the label to
verify, in which case all other labels are ignored.

| Parameter | Request | Response |
|---|---|---|
| `keyid` | MUST | MUST |
| `alg` | MAY (errata E01-11) | MAY |
| `created` | MUST (§5) | MUST |
| `expires` | MAY | MAY |
| `nonce` | MUST (§3) | MAY |

Signers emit present parameters in the order `keyid`, `alg`, `created`,
`expires`, `nonce`. No other parameter is defined. Signers MUST NOT emit
`tag` or any parameter not listed in §1. Verifiers MUST reject a signature
that carries one.

A verifier MUST reject a `Signature-Input` or `Signature` field value over
8 KiB, more than 32 covered components, or a header section over 64 KiB.

## 2. Signature base

One line per covered component, `<identifier>: <value>`, joined with `\n`,
followed by the `"@signature-params"` line. The `@signature-params` value is
the RFC 8941 serialisation of the inner list and its parameters. A verifier
MUST re-serialise the received member and MUST reject it if the received
bytes differ from that serialisation. Header identifiers are lower-cased and
quoted; multiple header values are joined with `", "` and trimmed. A request
or response with more than one field line of `Signature-Input`, `Signature`,
`Content-Digest` or `X-SAGE-DID` MUST be rejected. For other covered fields,
field lines are combined as RFC 9421 §2.1 specifies.

Of the derived components, signers MUST cover only `@method`,
`@target-uri`, `@authority`, `@scheme`, `@query`, `@status` (responses) and
their `;req` forms (responses). Header components are covered as this
section and §4 require. The `@query` value of a request without a query is
`?` (RFC 9421 §2.2.7).
Verifiers MUST reject a signature covering `@request-target`, `@path` or
`@query-param`. `@authority` is the lower-case host, followed by `:port`
only when the port is not the default for the scheme; a verifier MUST
reject a signature whose covered `@authority` value is not in that form.
`@target-uri` is the absolute URI the signer sent the request to (scheme,
authority, path and query, as sent). A verifier behind a proxy MUST
reconstruct it from its configured external origin, not from an internal
`Host`.

A covered component MUST NOT carry any parameter other than `;req`
(responses only). A verifier MUST reject `;sf`, `;bs`, `;key`, `;tr`,
`;name` and any unknown parameter.

## 3. Requests

A request signature MUST carry `nonce` and MUST cover `@method`,
`@target-uri`, `@authority`, and `content-digest` when the request has a
body. Signers SHOULD also cover `content-type`, `x-sage-did` and `date`, in
the order of the example:

```
"@method" "@target-uri" "@authority" "content-type" "content-digest" "x-sage-did" "date"
```

`content-digest` and `content-type` are omitted only when there is no body.
`x-sage-did` carries the signer's DID (`08-transport.md`).

`keyid` MUST be a did:sage DID valid under `06-did-sage.md` §1, optionally
followed by `#key-<n>` with `n` a decimal integer without leading zeros
(`did:sage:…#key-1`). Any other `keyid` MUST be rejected. In
0.9.0-draft.1.1 the fragment is informative. The verifier resolves the DID
and verifies with the single signing key chosen by `06-did-sage.md` §3.1
(first eligible secp256k1 key, else first eligible Ed25519 key). An agent
that holds both types can therefore be verified only with its secp256k1
key. The verifier derives the DID by splitting at the first `#` and MUST
check it against the expected sender (`ExpectedDID`) and, when the
transport carries `X-SAGE-DID`, against that header.

## 4. Responses

A response signature covers the response status and binds the request with
the `;req` parameter. The reference responder covers:

```
"@status" "@method";req "@target-uri";req "@authority";req
["content-digest";req] ["signature";req] ["content-type"] ["content-digest"]
```

`content-digest;req` is included when the request carried one, `signature;req`
when the request was signed, `content-type` when the response sets it, and
`content-digest` when the response has a body. `;req` is only valid in
response signatures; a request signature containing `;req` MUST be rejected.

A response signature MUST cover `@status`, `"@method";req`,
`"@target-uri";req`, `"@authority";req`, `"signature";req` (the request was
signed), `"content-digest";req` when the request carried one, and
`content-digest` when the response has a body.

A verifier MUST reject a signature that does not meet the requirements of
§3 and this section. There is no non-strict mode.

A client that sent a signed request to a responder known to sign responses
MUST treat a response without a valid response signature, including an
error response, as a failure and MUST NOT use its body.

## 5. Verification rules

1. Parse `Signature-Input` and `Signature` (§1, §2); select the label.
2. Check parameters and covered components (§1 to §4).
3. Check `keyid` (§3), derive its DID, and if `X-SAGE-DID` is present
   require it to equal that DID after canonicalisation (`06-did-sage.md`
   §2); check `ExpectedDID`, `ExpectedKeyID` and (requests only)
   `ExpectedAuthorities` when set.
4. Resolve the DID (`06-did-sage.md` §3); reject an unknown or inactive
   agent; select the key (`06-did-sage.md` §3.1).
5. Timing (see Timing below).
6. Rebuild the base from the received message (and the request, for a
   response) and verify the signature with the key's algorithm
   (`01-crypto.md`). Signature bytes: 64 bytes for Ed25519 and P-256,
   65 bytes for secp256k1 (`01-crypto.md` §2).
7. `Content-Digest` against the buffered body (see Content digest below).
8. Replay: check and reserve `(signer DID, nonce)` (see Replay below). This
   is the last step; a message that fails any earlier step does not consume
   its nonce.

### Timing

A signature without `created` MUST be rejected. A verifier MUST reject when
`now - created > MaxAge`, when `created - now > MaxClockSkew`, when
`expires` is present and `expires <= created`, or when `expires` is present
and `now >= expires`. `MaxAge` MUST be greater than 0 and at most 300
seconds (default 300). `MaxClockSkew` MUST be at most 300 seconds
(RECOMMENDED 60). Neither check can be disabled. Vectors are verified at
`now = created` (errata E00-08).

### Content digest

`Content-Digest` MUST contain exactly one member, `sha-256`, whose byte
sequence is 32 bytes; the digest is over the message content as transferred
(after any `Content-Encoding`). Any other member, a duplicate member, or a
body over 16 MiB MUST be rejected.

### Replay

After the signature verifies and every other check of §5 has passed, as the
last step, the verifier MUST check and reserve `(signer DID, nonce)` in its
replay store, where the signer DID is the canonical DID of `keyid`
(`06-did-sage.md` §2), and MUST reject a pair it has seen. It MUST retain
each pair at least until `created + MaxAge + MaxClockSkew`. A verifier that
has lost its replay store MUST reject signatures whose `created` precedes
the time the store was restored plus `MaxClockSkew`. When the store is full
it MUST reject new signatures rather than evict unexpired entries. A nonce
MUST be 16 to 64 characters of `ALPHA / DIGIT / "-" / "_"`; a canonical
UUID qualifies.

### Failure reporting

A verifier MUST answer every failure that occurs before the request reaches
the application handler (parsing, size, coverage, resolution, timing,
signature, digest, replay) with the same externally visible result: HTTP
401, the body `authentication failed`, and one constant `WWW-Authenticate`
field value chosen by the deployment (RFC 9110 §15.5.2 requires the field
on a 401). An endpoint that carries `08-transport.md` envelopes answers
instead with the result that `08-transport.md` §2 fixes for it (HTTP 200
and the unsigned failure object); 401 applies to every other endpoint. No
status, header or body may depend on which check failed. The
specific reason MAY be logged locally (`00-overview.md` §7, DP-6). A
library that returns detailed errors leaves this duty to its caller, which
MUST map them.

## 6. Open items

None. O-4 (RFC 9421 `tag` parameter) is closed by §1; application binding
is listed under Known residual risks. O-5 (a normative default
covered-component set for requests) is closed by §3 and §4.

## Known residual risks

- **No application binding with `tag` (E03-04).** A signature made with a
  SAGE key for another RFC 9421 application can be accepted by a SAGE
  verifier when its covered components happen to meet the rules of this
  chapter; a did:sage `keyid` limits this to keys registered for SAGE.
  Risk if left: low to medium.
- **The `keyid` fragment does not select the key (E03-16).** The verifier
  uses the key that `06-did-sage.md` §3.1 selects, so an agent cannot sign
  with its Ed25519 key while it has a secp256k1 key, and `#key-<n>`
  numbering is not stable. Risk if left: low.
