# 7. A2A agent card

Version: 0.9.0-draft.1.1. Finalizes 0.9.0-draft.1 with the errata in [../docs/errata-0.9.0-draft.1.md](../docs/errata-0.9.0-draft.1.md).

Vectors: `vectors/did.json` (`a2a-card-proof-ed25519`), `vectors/jcs.json`
(`agent-card-like`). Go sources: `pkg/agent/did/a2a.go`, `a2a_proof.go`,
`types_v4.go`.

## 1. Card

The card is the registry record of `06-did-sage.md` §3 projected into the
A2A / DID-core shape:

| Member | Content |
|---|---|
| `@context` | `["https://www.w3.org/ns/did/v1", "https://w3id.org/security/suites/ed25519-2020/v1", "https://w3id.org/security/suites/secp256k1-2019/v1"]` |
| `id` | the DID |
| `type` | `["Agent", "AIAgent"]` |
| `name`, `description` | strings |
| `publicKey[]` | one entry per *eligible* signing or key-agreement key (`06-did-sage.md` §3.1) |
| `service[]` | `{type, uri}` endpoints |
| `capabilities` | array of capability names (optional) |
| `created`, `updated` | RFC 3339 timestamps |

`service` always contains a `MessageService` entry with the record's
`endpoint`, followed by any entries of `capabilities.endpoints`. When the
record has no capabilities, `capabilities` is
`["message-signing", "message-verification"]`.

Each `publicKey` entry:

| Member | Content |
|---|---|
| `id` | `<DID>#key-<n>`, `n` as defined below |
| `type` | `Ed25519VerificationKey2020`, `EcdsaSecp256k1VerificationKey2019` or `X25519KeyAgreementKey2019` |
| `controller` | the DID |
| `publicKeyBase58` | base58 of the raw key bytes |
| `publicKeyHex` | hex of the same bytes |

Each `publicKey` entry MUST carry both. A verifier MUST reject a card in
which either is missing or they decode to different bytes. No multibase
encoding is used.

`n` is the 1-based position of the key in the record's full `keys[]` list,
so numbers can have gaps. A revocation reorders `keys[]` (the registry
moves the last key into the revoked position), so `#key-<n>` names a key
only for the card it appears in and MUST NOT be stored as a stable key
name.

## 2. Proof

```json
"proof": {
  "type": "Ed25519Signature2020" | "EcdsaSecp256k1Signature2019",
  "created": "<RFC 3339>",
  "verificationMethod": "<DID>#key-<n>",
  "proofPurpose": "assertionMethod",
  "proofValue": "<base58 signature>"
}
```

The signature is computed over the JCS canonical form (`02-jcs.md`) of the
card **without** the `proof` member, using the key named by
`verificationMethod`: Ed25519 over the canonical bytes, or secp256k1 with
the Keccak convention of `01-crypto.md`. `proofValue` is base58 of the raw
signature (64 or 65 bytes).

Because the whole `proof` object is outside the signature, a verifier MUST
NOT use `proof.created`, or any `proof` member beyond the checks of §3, for
freshness, ordering or display as signed data.

`Ed25519Signature2020` and `EcdsaSecp256k1Signature2019` are used here as
SAGE labels. The proof is a JCS signature with base58 `proofValue` and is
not a W3C Data Integrity proof; W3C verifiers will reject it, and a SAGE
verifier MUST NOT accept a W3C Data Integrity proof in its place.

## 3. Verification

1. Parse the card; keep the received JSON.
2. Parse `verificationMethod` as `<DID>#key-<n>`; its DID MUST equal `id`
   (canonical form, `06-did-sage.md` §2).
3. Exactly one `publicKey` entry MUST have that `id`; its `controller` MUST
   equal `id`; the pair (key `type`, proof `type`) MUST be
   (`Ed25519VerificationKey2020`, `Ed25519Signature2020`) or
   (`EcdsaSecp256k1VerificationKey2019`, `EcdsaSecp256k1Signature2019`); an
   `X25519KeyAgreementKey2019` key MUST NOT verify a proof; `proofPurpose`
   MUST be `assertionMethod`. These checks apply on every verification
   path.
4. Delete `proof` from the received JSON, canonicalise, and verify the
   signature with the key's bytes.
5. A verifier MUST NOT use a card to authenticate an agent, or take keys or
   endpoints from it, unless it has resolved `id`, found the agent active,
   and found the proof key among its eligible signing keys
   (`06-did-sage.md` §3.1). Verification without a resolver proves only
   that the card is internally consistent.

When a verifier uses a card, it MUST take signing and KEM keys from the
resolved record, not from `publicKey[]`, and MUST reject a card whose
`MessageService` URI differs from the record's `endpoint`.

The vector is verify-only because `proof.created` is the signing time.

## Known residual risks

- **E07-08**: The card signature does not cover the `proof` options, the
  proof types carry W3C names rather than SAGE-specific ones, and the card
  has no signed expiry, so an old card with an old endpoint verifies for as
  long as its key stays eligible. Risk if left: low to medium.
