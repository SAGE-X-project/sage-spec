# 3. HTTP Message Signatures profile

Vectors: `vectors/rfc9421.json`. Go sources: `pkg/agent/core/rfc9421/`
(`canonicalizer.go`, `verifier_http.go`, `parser.go`, `body_integrity.go`,
`response_signer.go`).

## 1. Headers

| Header | Content |
|---|---|
| `Signature-Input` | `<label>=(<components>);keyid="…";alg="…";created=…[;expires=…];nonce="…"` |
| `Signature` | `<label>=:<base64 signature>:` (RFC 8941 byte sequence, standard base64) |
| `Content-Digest` | `sha-256=:<base64 SHA-256 of the body>:` |

The default label is `sig1`. Signers MUST emit the parameters in the order
`keyid`, `alg`, `created`, `expires`, `nonce`, `tag`, omitting empty ones.
This profile assigns no meaning to the RFC 9421 `tag` parameter (open item
O-4), but verifiers MUST accept it and any other parameter they do not
know: the `"@signature-params"` line is the received member value, so a
verifier that re-serialises or drops parameters rejects conformant
signatures from other implementations.

## 2. Signature base

One line per covered component, `<identifier>: <value>`, joined with `\n`,
followed by the `"@signature-params"` line whose value is the parenthesised
component list and the parameters exactly as in `Signature-Input`, byte for
byte. Header identifiers are lower-cased and quoted; multiple header values
are joined with `", "` and trimmed.

Derived components implemented: `@method`, `@target-uri`, `@authority`,
`@scheme`, `@request-target`, `@path`, `@query` (an empty query yields `?`),
`@query-param`, and `@status` (responses only). `@target-uri` is the full
absolute URI. `@request-target` is the request target as it appears in the
request line (RFC 9421 section 2.2.5): for the origin form the path followed
by `?` and the query when present, never prefixed by the method. The
`request-target-ed25519` vector covers it together with `@path` and `@query`.

## 3. Requests

Signers SHOULD cover, in this order:

```
"@method" "@target-uri" "@authority" "content-type" "content-digest" "x-sage-did" "date"
```

`content-digest` and `content-type` are omitted only when there is no body.
`x-sage-did` carries the signer's DID (`08-transport.md`). Verifiers in
strict mode REQUIRE `@method`, `@target-uri`, `@authority`, `content-digest`
when a body is present, and a `nonce`.

`keyid` MUST be the signer's DID, optionally followed by `#<fragment>`
naming the key (`did:sage:…#key-1`). The verifier derives the DID by
splitting at the first `#` and MUST check it against the expected sender
(`ExpectedDID`) and, when the transport carries `X-SAGE-DID`, against that
header.

## 4. Responses

A response signature covers the response status and binds the request with
the `;req` parameter. The reference responder covers:

```
"@status" "@method";req "@target-uri";req "@authority";req
["content-digest";req] ["signature";req] ["content-type"] ["content-digest"]
```

`content-digest;req` is included when the request carried one, `signature;req`
when the request was signed, `content-type` when the response sets it, and
`content-digest` when the response has a body. `;req` is only valid in
response signatures; a request signature containing `;req` MUST be rejected.
Verifiers REQUIRE `@status` and, in strict mode, request binding.

## 5. Verification rules

1. Parse `Signature-Input` and `Signature`; the label to verify is given by
   the caller or is the lexicographically first label.
2. Rebuild the signature base from the received message (and the original
   request for responses).
3. Timing: reject when `now - created > MaxAge` (default 5 minutes; zero
   disables the check, which the vectors rely on), when `created` is more
   than `MaxClockSkew` (default 5 minutes) in the future, or when `expires`
   has passed.
4. Verify the signature with the algorithm implied by the resolved key
   (`01-crypto.md`). Signature bytes: 64-byte raw for Ed25519 and P-256,
   64 or 65 bytes (or DER) for secp256k1.
5. Only after the signature verifies, check the `nonce` against the replay
   guard scoped by `keyid` (a nonce seen twice under the same key is a
   replay). The window is the verifier's `MaxAge`.
6. Verify `Content-Digest` against the received body when it is covered.
   Bodies are buffered up to 16 MiB; larger bodies are rejected.
7. Check `ExpectedDID`, `ExpectedKeyID` and `ExpectedAuthorities` when set.

Any failure MUST be reported without revealing which step failed to the
sender beyond a generic authentication error.
